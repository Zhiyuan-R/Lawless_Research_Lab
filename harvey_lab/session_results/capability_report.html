Claude agent 法律任务能力诊断

基于 44 个已评分任务、127 条完整 agent trace，以及 113 条未通过标准的逐条归因。一句话结论：读材料和执行流程几乎没有问题，丢分主要在“律师判断”：轻重怎么定、站谁的立场、要不要主动补上材料里没写的法律风险。另外约四分之一的“失败”其实是评分标准本身的问题。

93.3%标准通过率（1,962 / 2,103）
8 / 44全部通过的任务（all-pass）
99.8%文档内容实际被读到的比例
0 / 113因为没读到材料而失败

“读到比例”的算法：把每份源文件中长度 ≥ 6 个字母的词去重，看有多少出现在 agent 实际看到的工具输出里。整行匹配会受 pandoc 版本和表格格式的影响而低估，所以用词级匹配。

强项与弱项

强：可以放心交给它

  • 完整阅读：127 个任务里，几乎每份文档都从头读到尾。超长输出被截断后，它会自己分段重读，或者回去打开溢出的文件。
  • 跨文档对账：主动建“文件之间的差异清单”，比如抓到 DIP 上限冲突、91 天到期日写反、6 份混进来的其他案件文件、对方摘要判决书里一个 $9,530,400 的计算错误。
  • 解析复杂格式：直接解开 docx 的 XML 读取修订痕迹，连对方没标出来的暗改也能找到（DPA 任务里找到 42 处标记修改和 17 处未标记修改）。
  • 事实抽取和引用：抽取类任务通过率很高，比如证词任务做了 60 多行带页码和行号的承认事项表。
  • 大规模检索：firm-knowledge 任务里把约 9,300 个文件全部转成文本，再用 rg 检索并逐个核实，召回很完整。
  • 按指令交付：文件名、格式、修订模式基本没有出错（113 条失败中 0 条属于没按指令做）。

弱：资深律师和它拉开差距的地方

  • 轻重校准（29 条）：自己定一套“阻断交割就是 Critical”的标准，然后把整类问题都升一级；对方有利的条款，只要“符合 playbook”就标成“合规”。
  • 不主动补充法律知识（27 条）：材料里没写的风险就不提，比如 Serta 式 uptier、充分保护弃权能否执行、MTCA 三倍赔偿、FTC Act §5、Part 744 的兜底审查。
  • 看到了却没用上（12 条）：playbook 里明写的警示、检查表里的某一行、10-Q 期后事项和股息之间的矛盾，都读到了，交付物里却没有。
  • 只从委托人视角看：从不站到对方的位置做压力测试，也很少拿外部市场惯例做参照。
  • 对指令理解过于字面：合伙人说“别加限定”，它就连必要的可执行性提醒也不写了。
  • 不愿给数字：明明读到了 >$12M、>$30M 的数字，却写“风险无法量化”。

113 条失败的归因

做法：独立的分析 agent 对照源文件、agent 的完整工具记录（看它是否“看见”某个事实）和交付物，逐条判断原因。覆盖 36 个有失败任务中的 29 个；剩下 7 个任务的 28 条没有归因，本页也没有引用它们。其中一组由两个 agent 各自独立归因了一遍，29 条里有 27 条原因判断一致（93%）。

评分标准本身的问题：约占失败的 24%

27 条失败中，交付物其实已经满足标准，或者标准和文件、法律相矛盾。按这个口径修正后，真实通过率大约是 94.6%，而不是 93.3%。典型情况：

tax/draft-tax-structure-memorandum · 8 条

标准要求按 §1363(d) 计算 338(h)(10) 下的 LIFO 回收税 $2.478M。agent 正确指出 §1363(d) 只适用于 C 转 S 的时点（这家公司 2000 年已经完成转换），而且 2022 年以后 §163(j) 用的是 EBIT 口径。agent 因为纠正了文件里的错误而被扣分。

international-trade-sanctions/draft-export-license-application · C-041

标准要求把新加坡写成 Country Group A:1。这个错误抄自筛查备忘录；agent 按 EAR 改成了 A:6/B，并说明新加坡不是瓦森纳成员。

bankruptcy-restructuring/draft-plan-effective-date-checklist · 4 条

KERP 相关的 4 条标准依赖“两名高管辞职、KERP 降到 $1.77M”这个事实，但所有文件的 XML 里都搜不到它，按现有材料不可能满足。

这也说明 LAB 的 all-pass 指标对标注噪声非常敏感：一个任务平均约 48 条标准，只要 1–2 条标准有错，就不可能拿到 all-pass。

115 / 127写完后回读校验过交付物

几乎所有 trace 都是同一个固定流程：先把全部文档转成文本 → 依次读完 → 把整份交付物写进一个 python-docx 脚本，一次生成（单条命令中位数约 33k 字符）→ 修格式。可以看到三个结构性问题：

缺少“实质复核”这一轮

写完之后的步骤几乎都花在修 $ 转义、列表编号和交叉引用上，几乎没有再对照指令和材料逐条核对轻重和遗漏。前面提到的“看到了却没用”（12 条）和“轻重校准”问题，正是这一轮本来能抓到的。

校验只看能不能打开

firm-knowledge/175 用没加引号的 heredoc 写 response.md，shell 把大部分 $金额 吃掉了，交付物里出现 “0.0M”“~40M” 这样的内容，agent 没有重新读一遍。“能打开、能解析”不等于“内容正确”。

优点和缺点同出一源：敢推翻材料

在税务、出口管制等任务里，它用自己的法律知识纠正了源文件中真实存在的错误，这是资深律师的特征。但在工资法、最终裁定等任务里，同样的倾向让它推翻了合理的基准数（比如用 $614,350 替换 $485,500，可能重复计算了一项），或者拒绝写出材料已经支持的结论。它在推翻材料时不区分“材料确实错了”和“只是口径不同”。

trace 里的推理过程（thinking）是加密的，无法分析，所以以上结论来自工具调用、工具输出和交付物，不来自它的“内心独白”。

对模型和 agent 的改进方向

  1. 加一轮复核：写完后对照指令和材料，按“每个问题的轻重、对方会怎么反驳、材料里提到但正文没写的点”逐条复查。这一步成本低，直接针对占失败 70% 以上的判断类问题。
  2. 把轻重标准锚定在外部：先从材料中提取客户或 playbook 给出的重要性门槛，再定档；不要自己发明一套分级。
  3. 默认做对方视角的压力测试，并引入市场惯例：每条“合规”结论都问一次“对方为什么会接受这个条款”。
  4. 主动提示学说层面的风险：针对每个领域准备一份“这一类文书律师默认会查的风险清单”（如 Part 744 兜底、Serta 式 uptier、可执行性），把它当成 skill 而不是靠模型临场回忆。
  5. 推翻材料时要区分两种情况：“材料错了”就明确纠正并说明理由；“只是口径不同”时，同时给出两种口径的数字。
  6. 工程侧：交付物不要用 heredoc 写；校验要比较内容（关键数字是否都在），不只看文件能否打开。

口径与局限

  • 样本：2,010 个任务中有 44 个已评分（覆盖 25 个执业领域，每个领域 1–3 个），另有 83 个只完成了作答、尚未评分，只用于统计工作方式。
  • 评分由同一会话中的独立 Claude 子 agent 担任裁判，不是官方的 Sonnet 4.6 + GPT-5.5 双裁判，分数不能和官方榜单直接比较。之前做过的 8 个任务复判中，逐条一致率为 99.3%。
  • 归因由 Claude 分析 agent 完成，判定“标准有误”的条目没有经过律师复核。
  • 数据与脚本：harvey_lab/analysis/（trace_stats.json、coverage.json、attribution/*.json）。
